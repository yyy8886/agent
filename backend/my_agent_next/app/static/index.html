工作流怎么写

把工作流理解成一条处理流水线：每个节点做一件事，做完后把结果交给下一个节点。

用户输入 → 梅贝尔提取参数 → 天气 Skill 查询 → 诺登整理回答

第一步：决定每个节点做什么

  1. 节点就是一个 Python 函数，例如“调用梅贝尔”。
  2. State是节点共用的数据袋，里面放用户输入、中间结果和最终回答。
  3. 连线决定执行顺序，例如 START → ask_agent → END。

第二步：从这个最小模板开始

下面只有一个节点：收到用户的 message，交给梅贝尔，然后把结果保存为 answer。

from typing import TypedDict

from langgraph.graph import END, START, StateGraph
from langgraph.runtime import Runtime
from my_agent_next.workflow_sdk import WorkflowRuntime


class State(TypedDict, total=False):
    message: str
    answer: str


async def ask_agent(state: State, runtime: Runtime[WorkflowRuntime]) -> dict:
    result = await runtime.context.call_agent(
        "mabel",
        {"message": state["message"]},
    )
    return {"answer": str(result.get("answer", ""))}


def build_workflow():
    graph = StateGraph(State, context_schema=WorkflowRuntime)
    graph.add_node("ask_agent", ask_agent)
    graph.add_edge(START, "ask_agent")
    graph.add_edge("ask_agent", END)
    return graph.compile()

第三步：逐句看懂模板

代码它在做什么
from typing import TypedDict导入一种“有固定字段的字典”类型，用来说明工作流中会保存哪些数据。
from langgraph.graph import END, START, StateGraph导入工作流图、开始标记和结束标记。后面用它们搭建执行顺序。
from langgraph.runtime import Runtime导入节点运行时对象。节点通过它使用应用提供的 Agent、Skill 和子工作流能力。
from my_agent_next.workflow_sdk import WorkflowRuntime导入本应用公开的工作流接口。用户源码只应通过这个入口访问应用能力。
class State(TypedDict, total=False):定义整个流程共用的数据袋。total=False 表示字段可以随着节点执行逐步加入。
message: str保存用户最初输入的文字。
answer: str保存工作流最终产生的回答。
async def ask_agent(...):定义名为 ask_agent 的异步节点。state 是当前数据，runtime 提供调用能力。
runtime.context.call_agent("mabel", ...)调用 ID 为 mabel 的 Agent，并把用户的 message 传给她。
result = await ...await 表示等待 Agent 回答完成，再把返回对象保存到 result。
return {"answer": ...}节点返回对 State 的更新：把 Agent 回答写入 answer 字段。
def build_workflow():工作流固定入口。应用通过这个无参数同步函数构建整张图。
StateGraph(State, context_schema=WorkflowRuntime)创建一张使用 State 保存数据、使用本应用 Runtime 能力的 LangGraph 图。
graph.add_node("ask_agent", ask_agent)把前面写好的函数注册为图中的一个节点，并给节点命名。
graph.add_edge(START, "ask_agent")规定流程开始后，首先执行 ask_agent 节点。
graph.add_edge("ask_agent", END)规定该节点执行完成后，整个流程结束。
return graph.compile()检查并编译图，然后把可运行的工作流返回给应用。

第四步：需要什么能力就调用什么

调用 Agent，用 Agent 的 ID，例如梅贝尔是 mabel：

result = await runtime.context.call_agent(
    "mabel",
    {"message": state["message"]},
)

调用 Skill 或工具，用它的名称并填写参数：

result = await runtime.context.call_skill(
    "weather-skill",
    {"city": state["city"]},
)

第五步：嵌套已有工作流

  1. 在编辑窗口点击“添加依赖”。
  2. 依赖键填写一个源码里使用的简称，例如 weather_query。
  3. 目标工作流选择“诺登天气查询”。
  4. 在节点中通过同一个依赖键调用：
result = await runtime.context.call_workflow(
    "weather_query",
    {"message": state["message"]},
    )

依赖键是当前工作流给子工作流起的简称，不是子工作流 ID。保存前点击“静态验证”可以查看语法、入口和导入问题。当前版本只能编辑和验证，执行 Worker 还未实现。

项目里的两个真实案例

案例一：诺登天气查询

用户问题 → 梅贝尔提取城市 → weather-skill 查询 → 诺登整理回答

工作流 ID：norden-weather-flow。它演示了一个 State 如何在三个节点间逐步增加 city、weather_result 和 answer。

  1. mabel_extracts_parameters 调用梅贝尔，只负责从用户问题中提取城市。
  2. weather_skill 独立调用天气 Skill，梅贝尔本身不需要绑定这个 Skill。
  3. norden_answers 把用户问题和真实天气结果交给诺登，生成最终答案。
result = await runtime.context.call_skill(
    "weather-skill",
    {"city": state["city"]},
)

案例二：小丑天气嵌套工作流

用户问题 → 小丑开场 → 案例一完整执行 → 小丑最终回答

工作流 ID：clown-weather-wrapper。它没有复制案例一的节点，而是把整个 norden-weather-flow 当成一个子工作流。

  1. 依赖配置把 weather_query 指向 norden-weather-flow。
  2. clown_opens 先调用小丑处理用户输入。
  3. norden_weather_workflow 通过依赖键执行整个案例一。
  4. clown_closes 根据案例一返回的天气答案生成最终回答。
result = await runtime.context.call_workflow(
    "weather_query",
    {"message": state["prepared_message"]},
)
